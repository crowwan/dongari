# 001. 서버 없이 기기 저장 + 백업 파일

## 상황

v1 은 localStorage 에 연도별 키(`accounting_YYYY`)로 형식 버전 없이 저장했다. 데이터 구조를 '월별 집계'에서 '거래 기록'으로 바꾸면서 저장 방식도 다시 정해야 한다. 사용자는 어머니 한 명, 기기는 스마트폰 한 대, 데이터는 1년에 기록 수백 건(수십 KB) 수준이다.

## 결정

서버 없이 기기(localStorage)에 저장하고, 저장소 계층을 인터페이스로 분리한다. 스키마 버전과 마이그레이션을 두고, 유실 대비는 PWA 설치 + `storage.persist()` + 백업 파일 공유로 한다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **localStorage + 백업 파일 (채택)** | 비용·운영 0, 로그인 없음, 오프라인, 데이터 크기에 충분 | 백업을 사람이 해야 함, 기기 간 동기화 없음 |
| IndexedDB | 큰 데이터·비동기 | 이 규모에선 이득 없음, 코드 복잡. 저장 계층 분리로 나중에 교체 가능 |
| 클라우드 동기화 (Supabase 등) | 기기 간 동기화, 원격 확인 | 로그인이 어머니에게 큰 장벽, 운영·비용, 개인정보 관리 |
| 로컬 + 자동 클라우드 백업 | 백업 자동 | 익명 백업 키 관리·서버 필요, 중간 복잡도 |

## 결과

- 쉬워지는 것: 오프라인 사용, 배포(정적 호스팅 그대로), 테스트(메모리 저장소).
- 어려워지는 것: 폰 교체 시 백업 파일을 직접 옮겨야 함. 가족이 원격으로 장부를 볼 수 없음.
- 사진 인식(SPEC-004)도 기기 안에서 실행하므로 서버 없는 구조가 유지된다 ([ADR 002](002-photo-recognition.md)).
- 다시 볼 조건: 백업을 안 해서 데이터를 잃는 일이 생기거나, 여러 사람이 함께 기록해야 하면 클라우드 동기화를 재검토한다(`LedgerRepository` 구현 교체).

## 스키마 버전을 올리는 기준 (2026-10-07, #77 날짜(일) 추가)

`Entry.day?`(1 ~ 그 달 마지막 날)를 더하면서 `schemaVersion` 을 2 로 둔다. 기준은 **옛 앱이 새 데이터를 잘못 읽거나 계산을 틀리면 올리고, 모르는 선택 필드를 덧붙이기만 하면 올리지 않는다.**

| 경우 | 버전 그대로(2, 채택) | 버전 올림(3) |
|---|---|---|
| 새 앱이 옛 저장 데이터·옛 백업 파일(날짜 없음)을 읽을 때 | 가드가 날짜 없는 기록을 그대로 받는다. 마이그레이션 없음 | 2 → 3 마이그레이션(버전 숫자만 바꿈)을 거친다. 결과는 같다 |
| 옛 앱(v2.1)이 새 데이터를 읽을 때 | 옛 가드는 모르는 칸(`day`)을 보지 않아 그대로 읽고 저장도 된다. 화면은 입력 순·날짜 없이 보이고 합계는 같다. 옛 앱에서 **고쳐 저장한 기록만** 날짜가 빠진다(옛 `updateEntry` 가 내용을 새로 만든다). 고치지 않은 기록은 객체째 저장돼 날짜가 남는다 | 옛 앱이 "새 버전 앱에서 쓴 기록이 있어요" 로 저장을 막는다(SPEC-002 상위 버전) |
| 옛 앱이 새 백업 파일을 불러올 때 | 그대로 불러온다(날짜는 안 보이지만 남는다) | "앱을 닫았다가 다시 연 뒤 불러와 주세요" 로 거부 |

- 옛 앱이 새 데이터를 만나는 실제 경우는 미리보기(`/dongari/preview/`, 새 앱)와 본 주소(옛 앱)가 같은 localStorage(`dongari:v2`)를 쓰는 릴리스 전 QA 기간이다(CLAUDE.md 미리보기 주의). 어머니 폰은 새 버전을 받아 두었다가 다음에 열 때 바꾸므로(SPEC-002 새 버전 반영) 옛 앱으로 되돌아가지 않는다.
- 버전을 올리면 그 기간 본 주소가 릴리스까지 저장을 막는다. 버전 그대로면 잃을 수 있는 것은 옛 앱에서 고친 기록의 날짜(일) 하나다. 막히는 쪽이 더 크다고 보고 그대로 둔다.
- 날짜 범위(1 ~ 장부 연도 그 달 마지막 날, 2월 윤년)는 같은 버전의 가드(`storage/schema.ts`)가 본다. 범위 밖이면 금액 범위 밖과 같이 깨진 데이터(기기: 옮기고 새로 시작, 백업 파일: "열 수 없어요")다.
- 다시 볼 조건: 칸의 뜻이 바뀌거나, 옛 기록에도 꼭 있어야 하는 칸이 생기거나, 옛 앱이 새 데이터로 합계·잔액을 틀리게 내는 변경이면 버전을 올리고 마이그레이션을 등록한다(`storage/migrate.ts` `MIGRATIONS`).

## v3: 장부 여러 개 (2026-10-08, #87 SPEC-005)

장부를 여러 개(동아리·모임 / 개인 가계부) 두려고 저장 형식을 `{ schemaVersion: 3, books: Book[], settings }` 로 바꾸고 `schemaVersion` 을 3 으로 올린다. 위 기준의 "옛 앱이 새 데이터를 잘못 읽는다"에 해당한다 — 옛 앱(v2)은 `ledgers` 가 없는 데이터를 형식이 다른 데이터로 보고 깨진 데이터처럼 옮겨 버린다. 올리면 옛 앱은 "새 버전 앱에서 쓴 기록이 있어요" 로 저장만 막는다.

```
StoredData { schemaVersion: 3, books: Book[], settings: Settings }   // 키 dongari:v2 그대로
Book       { id, name, kind: 'club' | 'household', ledgers: Record<연도, Ledger>, createdAt }   // books 는 만든 순
Ledger     { year, carryover, entries }                              // clubName 없음
Settings   { lastBackupAt?, lastChangedAt?, lastBookId? }
```

| 정한 것 | 고른 것 | 다른 안과 이유 |
|---|---|---|
| 장부 이름 자리 | `Book.name` 하나, `Ledger.clubName` 삭제 | 연도별 이름을 남기면 이름이 두 곳(장부·연도)이 되어 설정에서 무엇을 고치는지 헷갈리고 화면마다 어느 쪽을 보일지 정해야 한다. 지금 화면도 연도마다 다른 이름을 쓰는 흐름이 없다(설정은 "동아리 이름" 하나). 잃는 것: 연도마다 이름을 바꿔 쓴 경우 지난 연도 결산표 제목이 지금 이름으로 나온다 — 원본은 아래 보관 키에 남는다 |
| 옮길 때 이름 | 가장 최근 연도 장부의 동아리 이름 | 앱을 열면 보이던(올해) 이름. 이전 연도 이름은 위 이유로 버린다 |
| 옮긴 장부 id | 고정 `book-1` | 같은 v2 데이터를 다시 열어도(저장 전) 같은 장부. 새로 만드는 장부는 `crypto.randomUUID` 라 겹치지 않는다. 백업 불러오기는 전체 바꾸기라 섞이지 않는다 |
| 옮긴 장부 만든 시각 | 옮긴 시각 | 장부를 만든 시각은 v2 에 없다. 순서는 배열 순(만든 순)이라 값은 표시용 |
| 지금 장부 | `settings.lastBookId` (없거나 지워졌으면 첫 장부) | 화면 상태로만 두면 앱을 다시 열 때 잃는다(AC-2). 저장 데이터에 두면 장부를 바꾸는 길이 "이 값을 바꿔 저장" 하나다 |
| 키 이름 | `dongari:v2` 그대로 | 키를 바꾸면 이미 설치한 앱이 옛 키를 찾아 옮겨야 하고, 미리보기·본 주소가 같은 키를 쓰는 규칙(CLAUDE.md)도 바뀐다. 버전은 `schemaVersion` 이 말한다 |
| 옛 데이터 보관 | 옮겨 읽을 때 원본 글자를 `dongari:v2:schema-2` 에 그대로(같은 원본이면 다시 쓰지 않음, 지우지 않음) | 저장 전까지는 원래 키도 v2 그대로라 열 때마다 옮긴다. 보관하지 못하면(용량 등) 옮긴 기록은 보여 주되 저장을 막아(`read-only`, `old-version-unpreserved`) 원본을 덮지 않는다. 백업 파일 보내기는 된다. 백업 불러오기는 사용자가 바꾸기로 한 것이라 막힘을 푼다 |
| 형식이 틀린 v2 | 깨진 데이터와 같이(원본을 `broken` 키로 옮기고 새로 시작) | SPEC-002 깨진 데이터 규칙 그대로 |
| v2 백업 파일 | 같은 `migrate` 로 장부 하나로 읽는다 | 저장소와 백업 읽기가 한 길을 쓴다(#8) |

- 미리보기 QA 영향: 미리보기(새 앱, v3)를 연 브라우저에서는 본 주소(옛 앱, v2)가 v3 데이터를 만나 저장을 막는다(SPEC-002 상위 버전). QA 는 지금처럼 테스트용 폰·브라우저로 한다(CLAUDE.md 미리보기 주의).
- 다시 볼 조건: 장부별 백업·장부 사이 옮기기(SPEC-005 범위 밖)가 생겨 장부 id 가 섞일 수 있으면 옮긴 장부 고정 id 를 다시 본다.
