# 006. 자동 보관 상태 신호를 서버에 평문으로 남기고 GitHub Actions 로 매일 점검

## 상황

[ADR 005](005-cloud-keep.md)의 자동 보관은 실패해도 조용히 기다린다. 서버가 깨지거나 앱 버그로 보관이 멈춰도 사용자도 개발자도 모른다. 사용자는 어머니와 가족 몇 명이라 앱 안 안내만으로는 대처를 기대하기 어렵고, 개발자가 알아야 한다(2026-10-15 사용자: "이건 사용자가 아니라 내가 볼 수 있어야 할 것 같은데").

ADR 005 는 "서버에는 암호문과 이름(해시)만" 이었다. 폰 쪽 보관 상태를 개발자가 보려면 그 원칙에 예외가 필요하다.

## 결정

1. 앱을 열 때 폰이 **상태 신호**(자동 보관 켜짐, 밀린 변경이 생긴 때, 마지막 보관 시각, 너무 큼, 앱 버전)를 평문으로 서버에 보낸다. 장부 내용·복구 코드는 넣지 않는다. 서버는 받은 때를 붙여 이름별로 덮어쓴다.
2. GitHub Actions 예약 워크플로가 하루 한 번 비밀 토큰으로 요약을 받아 판정하고, 문제가 있으면 실패해서 GitHub 실패 메일로 알린다. 자세한 동작은 [SPEC-007](../specs/SPEC-007-keep-watch.md).

- ADR 005 의 "서버는 내용과 복구 코드를 모른다" 는 그대로다. 새로 서버에 남는 것은 **사용 흔적**(언제 앱을 열었는지, 언제 마지막으로 보관했는지, 앱 버전)이다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **상태 신호 + GitHub Actions 메일 (채택)** | 이미 쓰는 GitHub 메일로 알림, 추가 서비스 없음, 서버 고장과 폰 쪽 실패를 둘 다 잡음 | 사용 흔적이 평문으로 서버에 남음, 앱을 안 열면 폰 쪽 상태를 모름, 60일 활동 없으면 예약 워크플로 멈춤 |
| 앱 안 안내만 (SPEC-006 7일 띠) | 서버 변경 없음 | 개발자가 모름, 사용자 대처에 기대야 함 |
| 서버 상태만 바깥에서 확인 (업타임 체크) | 앱 변경 없음, 평문 정보 없음 | 서버는 멀쩡한데 폰에서 못 올리는 경우(앱 버그·CORS)를 못 잡음 |
| Cloudflare Cron Trigger 에서 바로 알림 | GitHub 예약 멈춤 걱정 없음 | 메일은 도메인(Email Routing) 필요, 푸시는 ntfy 등 외부 서비스 필요 |
| Sentry 등 오류 수집 서비스 | 앱 오류 전반을 봄 | 사용자 몇 명에 과함, 가입·SDK·개인정보 검토 |

## 결과

- 쉬워지는 것: 보관이 3일 넘게 밀리거나 서버가 죽으면 다음 날 아침 메일로 안다.
- 어려워지는 것: 비밀값 하나(`REPORT_TOKEN` / `KEEP_REPORT_TOKEN`)를 Worker 와 레포 양쪽에 맞춰 둬야 한다. 서버에 사용 흔적이 남는다(Cloudflare 와 토큰을 가진 사람은 볼 수 있음).
- 다시 볼 조건: 사용자가 가족 밖으로 늘어나면 상태 신호를 끄는 설정이나 알림 범위를 다시 본다. GitHub 예약 멈춤이 반복되면 Cloudflare Cron Trigger 로 옮긴다.
